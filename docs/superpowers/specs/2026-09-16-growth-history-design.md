# C 盘空间分析工具 — 历史快照与增长趋势设计文档（v3）

日期：2026-09-16
状态：待用户审阅
基于：v2 设计文档（`2026-09-15-c-drive-cleaner-design.md`，单次扫描只读分析）

## 1. 背景与目标

v2 已实现单次扫描的只读分析（scan-result.json 缓存）。但单次快照只能看到"当前多大"，看不到"涨了多快、涨在哪"。

v3 新增「历史快照与增长趋势」子系统：

- **记录**：每次扫描后，把 C 盘**全目录树**的大小快照存下来，长期积累
- **趋势**：对比历史快照，计算各目录在 1年/6月/1月/15天/10天/5天/2天/1天/自定义小时 窗口内的增长量
- **洞察**：增长量排行 + 持续膨胀双标记，定位活跃膨胀目录（如钉钉聊天记录无限增长），预判空间不足
- **管理**：快照由用户按年/月/日/时维度手动筛选删除，避免历史数据自身侵占空间

### 1.1 需求确认结论（brainstorming）

| 决策点 | 结论 |
|---|---|
| 记录粒度 | **全目录树**（C 盘所有目录，支持逐层下钻定位） |
| 保留策略 | **仅手动按时间删除**（不做自动清理） |
| 重点判定 | **增长量排行 Top N + 持续膨胀双标记** |
| 权限不足目录 | 保持"跳过+标注"，UI 提供**一键以管理员身份重启并自动重扫**（UAC 弹窗，一次性提权） |

### 1.2 核心安全原则（延续 v2，不因新增功能改变）

1. 扫描与快照全程只读：绝不删除、移动、修改任何文件/目录/注册表项。
2. 权限不足的目录：跳过并标注「未扫描」，绝不提权、不夺取所有权。
3. "以管理员身份运行"仅为**引导提示**，由用户自行选择是否重启应用提权。

## 2. 存储结构

新增 `history/` 目录，与 `scan-result.json` 解耦：

```
history/
├── index.json                  # 元数据索引（快照清单，供列表/删除/一致性校验）
├── 2026-09-16T10-30-00.tsv.gz  # 每次扫描一个全树快照（TSV + gzip）
└── ...
```

- 快照文件名 = 时间戳 ID（`YYYY-MM-DDTHH-mm-ss`），天然按时间排序
- 删除一个快照 = 删除一个文件 + 更新 index.json

## 3. 数据模型

### 3.1 index.json

```json
{
  "snapshots": [
    {
      "id": "2026-09-16T10-30-00",
      "scannedAt": "2026-09-16T10:30:00",
      "disk": { "totalGB": 477, "usedGB": 120, "freeGB": 357 },
      "dirCount": 412300,
      "fileCount": 1100000,
      "fileSizeMB": 34.5,
      "unscannedDirs": 5,
      "warning": null
    }
  ]
}
```

字段说明：
- `id`：快照文件名（时间戳）
- `dirCount / fileCount`：统计信息，展示用
- `fileSizeMB`：快照文件压缩后大小
- `unscannedDirs`：本次快照中因权限不足未计入的目录数
- `warning`：快照生成失败时的非致命警告信息

### 3.2 快照文件（`<id>.tsv.gz`）

每行一个目录：`目录绝对路径<TAB>总字节数`，路径统一小写，按路径排序存储。

```
c:\  100000000000
c:\program files  51234000000
c:\program files\microsoft  1200000000
c:\users  34000000000
c:\users\zhangsan\appdata\roaming\dingtalk  5600000000
...
```

- **粒度**：目录级（几十万行），非文件级（几百万行）——满足逐层下钻，体积可控
- **字节数** = 该目录含所有子孙文件的总大小
- **未扫描目录**：`大小<TAB>` 缺省，即 `path<TAB>`（空字节数）或用 `-1` 标记

## 4. 扫描流程变更

```
POST /api/scan
  → runScan()                    # 现有 PS 只读扫描 → scan-result.json（不变）
  → buildSnapshot()              # 新增：Node 端全树快照
       robocopy C:\ NULL /L /E /XJ /BYTES /NP /NC /NJH /NDL /R:0 /W:0
       → 流式解析文件行（大小+路径）→ 自底向上累加目录大小（Map<path, bytes>）
       → 写入 history/<id>.tsv.gz + 更新 index.json
```

关键点：
- **快照捕获失败不阻塞主流程**：主扫描结果照常返回，`index.json` 记录 `warning`，UI 展示提示
- robocopy `/L` 只列出不复制，延续只读原则；`/XJ` 跳过 junction 防循环

## 5. 增长分析算法

### 5.1 基础差值（选定窗口 W）

- 从 index 找距离当前**最近但不晚于** `now − W` 的历史快照 `S_old`（向前取，不取未来）
- 对每个目录 d：`growth(d) = size(latest, d) − size(S_old, d)`
- 三态：
  - `S_old` 无此目录（新增）→ `growth = size(latest, d)`
  - `latest` 无此目录（已删除）→ `growth = −size(S_old, d)`
  - 任一快照中该目录未扫描（null）→ 跳过，不参与排行

### 5.2 时间窗口

预置：`1y / 6m / 1m / 15d / 10d / 5d / 2d / 1d`；自定义：N 小时。

窗口对应的历史快照不存在时（如要 1 年但最早只有 60 天）→ 用最早可用快照代替，响应标注 `actualWindowDays`，UI 提示"实际覆盖 X 天"。

### 5.3 双标记

1. **增长量排行**：窗口内 `growth` 最大的 Top N（默认 20，可调），全树范围不限层级，降序展示
2. **持续膨胀**：锚点窗口 1天 / 7天 / 30天（内部固定窗口，独立于展示用时间窗口）同时满足：
   - 三个锚点窗口 growth 均 > 0
   - 30 天增长 > 阈值（默认 1GB）
   → 标「持续膨胀」，用于抓钉钉聊天记录这类慢速但稳定的膨胀源

### 5.4 活跃程度分档（基于最近窗口增长量）

| 档位 | 颜色 | 判定 |
|---|---|---|
| 极高 | 🟥 | 窗口增长 > 5GB |
| 高 | 🟠 | 1GB ~ 5GB |
| 中 | 🟡 | 100MB ~ 1GB |
| 低 | 🟢 | < 100MB |

### 5.5 逐层下钻

从任意目录开始，返回其直接子目录明细（当前大小、窗口增长、活跃档、标记、是否有子目录），逐层下钻定位到具体膨胀目录。

### 5.6 目录趋势序列

返回某目录在全部快照中的 `(time, size)` 序列，抽样最多 60 个点，供趋势折线图展示。

## 6. UI 设计

沿用 Figma 深色仪表盘风格。侧边导航新增两项：

| 导航项 | 页面 | 内容 |
|---|---|---|
| 趋势分析 (Trends) | `Trends/index.tsx` | 增长排行 + 双标记 + 逐层下钻 + 趋势折线图 |
| 历史快照 (History) | `History/index.tsx` | 快照列表 + 按年/月/日/时筛选 + 手动删除 |

### 6.1 趋势分析页

- 顶部：时间窗口 Segmented（1年/6月/1月/15天/10天/5天/2天/1天 + 自定义 N 小时）
- 主区「增长排行 Top N」（全树范围）：
  - 每条：完整路径（层级缩进）、当前大小、窗口增长量、活跃程度色点、持续膨胀徽标
- 点击条目下钻：面包屑 + 子目录表格（目录名、当前大小、增长量、活跃档、标记、子目录数），可继续下钻
- 选中目录后右侧展示趋势折线图（历史大小序列）
- 数据不足（快照 < 2 条）时展示引导提示

### 6.2 历史快照管理页

- 顶部：年份 / 月份 / 日期 / 小时 Select 组合筛选（任意组合，即"按年/月/日/时维度"）
- 快照表格：时间、磁盘已用、目录数、文件数、快照大小
- 操作：单条删除（二次确认）、筛选结果「删除当前筛选结果」批量删除
- 顶部显示快照总占用空间

### 6.3 一键提权重启（UAC）

概览页存在未扫描目录（`unscannedDirs > 0`）时，提示条提供「一键以管理员身份重扫」按钮：
- 点击触发系统 UAC 授权弹窗；确认后旧服务退出，以管理员身份启动新服务并自动重新扫描（`--scan-on-start`），完成后页面自动刷新数据
- 一次性提权：之后普通「重新扫描」均在管理员模式下执行，不再弹 UAC
- UAC 取消/超时（60s）：旧服务保持运行，提示「授权被取消」，可重试或手动以管理员身份运行

## 7. API 设计

server 拆出 `server/history.js`（保持 server/index.js 只负责路由与静态托管）：

| 接口 | 说明 |
|---|---|
| `POST /api/scan`（改造） | 扫描完成后自动 `buildSnapshot()` 追加历史快照；快照失败仅记 warning |
| `GET /api/history` | 返回 index.json 快照列表 + 总占用 |
| `DELETE /api/history` | body：`{ ids: string[] }` 或筛选 `{ year, month, day, hour }` / `{ before }`；删除文件 + 更新索引，返回删除数 |
| `GET /api/growth?window=30d&top=20` | 全树增长 Top N：`{ window, scannedAt, compareAt, actualWindowDays, entries: [{ path, size, growth, tier, sustained }] }` |
| `GET /api/growth/dir?path=c:\windows&window=30d` | 直接子目录增长明细（下钻） |
| `GET /api/growth/trend?path=...&points=60` | 某目录历史大小序列 |

server/history.js 内部模块：
- `buildSnapshot()` — robocopy 全盘列表 → 自底向上累加 → 写 TSV.gz + 更新索引
- `loadSnapshot(id)` — 流式读 TSV.gz → Map<path, bytes>
- `computeGrowth(window, top)` — 双快照差值、分档、双标记
- `deleteSnapshots(filter)` — 按条件删文件 + 更新索引

window 参数解析：`1y / 6m / 1m / 15d / 10d / 5d / 2d / 1d / <N>h`。

## 8. 边界情况

| 场景 | 处理 |
|---|---|
| 首次扫描（仅 1 条快照） | 增长接口返回"历史数据不足"，UI 引导继续扫描积累 |
| 窗口无对应历史快照 | 用最早可用快照代替，UI 标注实际覆盖天数 |
| 目录删除/新增 | 明细中负增长 / 按全额增长计入 |
| 权限不足目录 | size 为 null，跳过排行，明细标注「未扫描」 |
| 快照生成失败 | 不影响主扫描结果，index 记 warning |
| 手工删除快照文件 | 加载 index 时一致性校验，自动过滤失效项 |
| 删除全部快照 | 增长接口返回空，UI 提示重新扫描 |
| 快照文件被删但 index 未同步 | `GET /api/history` 时校验文件存在性，自动修正索引 |

## 9. 性能预算

- **快照生成**：robocopy /L 全盘文件列表（约 1~2 百万行），Node 流式解析 + 累加 + gzip 写入，预计 10~60 秒；不阻塞主扫描返回
- **增长计算**：两份快照各几十万行，流式读 + Map 差值，秒级
- **内存**：单快照解压后 Map 约几十万 key，可接受
- **磁盘**：单快照压缩后约 10~40MB，由用户手动清理

## 10. 测试与验证

- 实机扫描两次，验证第二次扫描后 `GET /api/growth?window=1d` 能算出两个顶层目录间的小规模增长
- 验证未扫描目录（如 System Volume Information）不参与排行、正确标注
- 验证历史快照管理页按年/月/日/时筛选与删除（单条 + 批量），删除后 index 正确
- 验证快照 < 2 条与窗口数据不足时的引导提示
- 验证手动删除快照文件后 `GET /api/history` 自动修正索引
- 前端遵循用户约定：每次编辑后 `npx tsc --noEmit` 检查；已知预存错误清单除外
- 增长计算结果与 robocopy 顶层大小交叉核对（数量级一致）
